# 0.4.5：多配件套装“刚保存即缺失”调查

用户反馈Shattered Royal Armor加入套装后显示缺失，随后确认是刚保存就出现。本轮修正一个可在匹配逻辑中复现的失效条件，并增加真实库存诊断。没有反馈者的日志/库存实例，不能认定该模组的故障原因已最终确认。

## 配件数量核对

读取本机安装的原版1.4及其CHS覆盖`ShatteredRoyalArmor.esp`，两份均有49个ARMO记录，主要是三种材质的配件，使用17种槽位组合；头发使用31/41，其余包括32、33、34、35、37、38、42、45、47、48、49、54、55、57、58、59。49是插件总记录数，不代表玩家一次穿戴49件。护甲记录未发现VMAD脚本或TNAM模板；这不排除其他模组脚本/补丁改变装备。

预设限制是每套实际穿戴64件、最多100套，Capture与Decode均检查。超过64会在保存阶段拒绝，不是保存成功后显示缺失。没有仅允许原版护甲槽位的过滤；非盾牌ARMO配件都被采集。因此本机版本的数据和代码没有支持“配件数量本身导致缺失”的证据；其他版本/补丁仍需实际信息。

## 明确修正的匹配问题

原`Match`：两个候选均满足完整`Same`签名时，如果保存项有强化/实例附魔/改名，即返回歧义，即使两份无UID且一份正穿戴。Capture仍允许保存，而下一次Entries校验将整个预设标为不可用。例如某个配件强化至同一数值的两份副本，保存穿戴项后会立即失败；有更多配件只是增加碰到这种条件的机会，不是数量限制。

0.4.5：没有UID且完整签名相同的副本视为等价，优先已穿戴项；UID非零仍要求精确身份，重复UID匹配仍拒绝。原base/enchantment/health/customName/UID/owner比较和强化容差不变，不回退到同Form的不同强化/附魔/改名实例；不同UID也不替换。导入的跨角色中性配方仍沿用原有严格歧义预检。

显示名称生成可能更新ExtraTextDisplayData，Describe现在先取得显示名，再记录身份字段。Capture对当前穿戴快照先Resolve，不能解析则拒绝保存、保留已有预设并记录原因；不改FWO 1或co-save结构。已有预设不自动重写，符合修正条件的旧预设可直接重新解析；实际属性已变化仍需覆盖记录。

## 诊断与性能

Resolve给出第一失败配件及原因：基础物品不在库存、基础存在但实例字段不一致、UID碰撞/歧义、配方重复指向同一候选。详情卡用可翻译原因和该配件的保存名称显示；状态标记仍沿用原“缺失/歧义”文案。

Entries失败时日志输出`Outfit validation`（阶段、预设ID/名称、件数、失败序号、base/local/runtime ID、UID/owner、附魔、强化、改名）及最多4个同base候选的字段，并记录候选总数。相同预设的相同失败类型/序号只在状态改变或重新加载/覆盖后报告，避免反复进入轮盘刷日志。Capture及执行前检查失败也报告。以前UI直接禁止点击失效项，执行前日志往往根本不会产生，本轮覆盖该诊断缺口。

不增加每帧扫描，不采集更多inventory对象；失败原因额外遍历只发生失败项，候选仍来自原快照。装备事务、任务超时、盾牌/任务物品保护及菜单/输入逻辑不改。日志缓存受Outfits互斥保护，读档/恢复/覆盖/删除清除对应记录；Capture失败前不修改presets。

## 本地验证及待实测

OutfitTests新增64件合成配件序列化/解析/穿戴判定、65件保存拒绝、有强化/附魔/名称的无UID等价副本优先穿戴、卸下后仍可解析、字段不一致拒绝、新增UID拒绝、真正缺物/UID歧义/重复配方原因与失败序号、成功后清除旧诊断。测试通过；这不是49件真实Shattered库存的游戏内复现。

Release编译与OutfitTests、SettingsTests、WheelLogicTests、InventoryTests、RuntimeLayoutTests通过。RuntimeLayoutTests覆盖五种模拟运行时布局、地址库格式1/2/5夹具及实际0.4.5 DLL元数据，不代表五种游戏实测；没有新增地址/hook，因此不重复真实地址库全扫描。InventoryTests的60018项合成目录分页检查通过，不能代替游戏内性能测试。新UI文案沿用已有详情卡换行/裁剪，不改变绘制。未启动游戏、未修改第三方护甲/本地存档；本机co-save中只有其他护甲的预设，不能替代反馈者的失败现场。

实际Draw代码的WARP离屏`outfit-missing`场景通过720p英文、1440p中文长配件名称验证：详情卡换行及边界正常，字体预热/复用、遮罩与稳定扇区不透底检查通过。使用合成数据，非游戏截图；未改变生产绘制代码。

请让反馈者用0.4.5打开已有预设，或穿上对应配件后新建/覆盖。确认立即识别、换装/卸下、保存读档及武器/盾牌保留。若仍失效，提供详情卡指出的配件与FavoriteWheel.log的`Outfit validation`/`Outfit candidate`段，并说明是否强化/附魔/改名、是否有多份同款。此时可区分真实缺物、UID新增/重复、属性变化及配方重复；不能仅凭模组名称做例外放行。
